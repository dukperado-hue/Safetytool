# Transformation mapping table

Implemented in `js/transform.js` (registry `TRANSFORMS`). Each one has a **preview** (nothing is created) and an **apply** step that refuses to run until the destination validates and every listed confirmation is given. Generated content is marked `prov.origin = "generated"`, `reviewed = false` (or recorded as a `proposed` link). Destination fields that need a human decision stay **empty**.

| Transformation | Source → destination | Copied directly | Transformed | Not transferred | Links recorded | Needs confirmation |
|---|---|---|---|---|---|---|
| `bowtie-to-swiss@1` (existing behaviour, unchanged) | Bowtie route → Swiss | hazard text; control text → layer name/defence; escalation factor → latent hole; loss = chosen consequence or top event | each control → one layer (`controlId`), each escalation → one hole (`escalationId`) | other routes, control state/adequacy/reliability/owner/evidence, ERC, ADREP; **trajectory left empty** | `derived_from` (confirmed, by transformation) | none (decision: threat; optional consequence) |
| `bowtie-to-stamp@1` | Bowtie → STPA | consequence text → proposed loss; top-event text → one proposed hazard | hazard → all proposed losses (as the bowtie structure says); bowtie controls listed in the hazard notes | system/boundary, constraints, control structure, control actions, feedback, UCAs, scenarios (not in a bowtie); threats, escalations, states, owners, evidence | `candidate_mapping` (proposed) loss/hazard; `references` (proposed) hazard → control | system left empty · hazard is an event not a state · losses may be intermediate events · hazard→loss links are copied, not an STPA finding |
| `bowtie-to-fram@1` | Bowtie → FRAM | control text → function name; owner → a Resource item (generated) | escalation factor → ANTICIPATED variability (generated, unreviewed) | Input/Output/Precondition/Control/Time (stay `unknown`); **couplings** (path order is not output→input); threats, consequences, hazard, top event, states, evidence | `candidate_mapping` (proposed) | activity left empty · aspects unknown · variability comes from escalation factors, not observation |
| `swiss-to-hfacs@1` | Swiss → HFACS | hole text → UNCLASSIFIED factor; loss text → occurrence | hole type and any `hfacsLevel` hint written in the factor notes only | HFACS categories (**never assigned automatically**), influences, evidence, layers, hazard, trajectory | `derived_from` (confirmed) hole → factor; `candidate_mapping` (proposed) loss → occurrence | categories to be chosen by the analyst · occurrence text is an outcome |
| `fram-to-bowtie-stamp@1` | FRAM → Bowtie / STPA | — | — | everything | — | **UNSUPPORTED.** A function or coupling does not say which threat, barrier, control structure or constraint it matches; any automatic mapping would be a guess. Create a link yourself (`candidate_mapping` / `references`). |
| `event-records-to-pyramid@1` | CSV → Accident Pyramid | `id, date, category, reference, note` → records | label matched to existing tiers; unseen labels stay uncategorised unless the analyst creates tiers | extra columns (reported); invalid dates are dropped from the date field and noted | history entry (file name, content hash, row count); each record carries `importId` | preview first; duplicates are flagged as *possible* only |

Direction and meaning of every relation: `docs/INTEROP.md`. Validation: each destination is checked with its own validator; lint then lists everything still unfinished (for example the empty STPA system is still an error in lint).

**Not promised:** complete bidirectional conversion. The methods answer different questions (barriers vs. system control vs. activities vs. human-factors classification); these mappings give *starting points* with their limits stated.
